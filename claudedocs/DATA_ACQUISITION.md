## 結論

- Yahooのブロック・HTML変更で最も不安定なのは、日本語概要・業績予想・信用倍率など `finance.yahoo.co.jp` のHTMLを読む経路。
- 株価・財務はYahooグローバル側をyfinanceで取得しており、日本版HTMLとは別経路。429、タイムアウト、一時的な空レスポンスは起きるが、日本語概要より取得実績は安定している。
- 株主・役員はブロックだけが原因ではない。日本の新興・小型・TOKYO PRO Market銘柄は、yfinance、yahooquery、Strainer、J-LiC側に未収録のことが多い。
- 設立日はYahoo日本版プロフィールへの依存が強い。上場日はyfinanceの初回取引日で補えるが、正本はJPXとする。
- 無料でかなり改善できる。中心はEDINET、JPX、TDnet、会社IR。ただし全銘柄・常時最新・完全自動・再配信条件まで無料で保証することはできない。

## 実装済みの欠損対策

### 1. 空データで正常値を消さない

`analysis_quality.py` が財務履歴に値があるかを確認し、空の履歴は保存対象から外す。`financial_history` と `cf_history` の両方に値がある場合だけ `data_status=fresh` とする。

### 2. 原因を保存する

`screened_latest.source_status JSONB` を `supabase/migration_source_status.sql` で追加済み。ユーザーが2026-08-03に本番DBへ適用済み。

主な状態:

- `success`: 取得成功
- `no_data`: HTTP 404や取得元に値がない
- `rate_limited`: HTTP 403/429等
- `timeout` / `network_error` / `source_error`: 通信・取得元障害
- `disabled` / `circuit_open`: Yahoo日本版を意図的に停止
- `skipped`: 高速バッチ等で処理を省略

### 3. Yahoo日本版のサーキットブレーカー

`yahoo_jp_guard.py` に統一。403、429、5xx等が5回連続したら、そのプロセスからYahoo日本版への追加アクセスを止める。404は「未収録」として扱い、ブロック判定には含めない。大量処理中は `SKIP_YAHOO_JP=true` で最初から無効化できる。

### 4. 164A アップルパークの公式補完

`official_company_profiles.py` に、公式開示で確認した値を欠損時だけ補うキャッシュを追加済み。外部取得で値が取れた場合は上書きしない。

- 設立日: 1991-08-07
- 上場日: 2024-03-25
- 市場: TOKYO PRO Market
- 日本語概要、所在地、代表者、主要株主、役員も補完
- 設立・上場の出典: JPX「新規上場会社概要」
- 株主・役員の出典: 会社の株主総会招集通知

### 5. スコアと表示

- 欠損項目を不合格として減点しない。
- 判定できた項目が6未満ならスコアを出さない。
- 判定項目数とデータ充足度を併記し、欠損がある100点は暫定評価と表示する。
- `/screener`でも詳細画面と同じ判定を使い、充足度100%未満のスコアはオレンジ、100%の確定評価だけ緑で表示する。ホバー時に充足度と判定項目数を表示する。
- レポートは不足セクションを明示し、取得できたデータだけで構築する。

## 改善後の取得アーキテクチャ

ユーザーの画面表示時に複数サイトを同期スクレイピングしない。画面はDBの最後の正常値を返し、取得・更新はバックグラウンドで行う。

```text
閲覧リクエスト
  → screened_latest の最後の正常値を即時表示

更新ジョブ
  → 公式・安定ソース
  → Yahoo系の最新値
  → 取得結果の検証
  → 正常値だけ更新
  → source_status / source / as_of / fetched_at を保存
```

各フィールドは最低限、次を持つ。

- `value`: 表示する値
- `source`: 取得元
- `as_of`: 情報の基準日
- `fetched_at`: 取得日時
- `status`: 成功、未収録、制限、タイムアウト等
- `is_stale`: 古い値を表示しているか

当面は既存の列と `source_status JSONB` を拡張し、必要性が見えてから履歴テーブルを追加する。最初から大規模な新テーブルに分割しない。

## データ別の改善案

### 日本語概要

推奨順序:

無料枠と現在の取得実績を優先し、実装順は次のとおり。

1. Yahoo日本版から日本語概要
2. 失敗した場合だけ `yahooquery → yfinance` から英語概要
3. 英語概要をGPTで200文字以内の日本語へ要約
4. 新規上場・TOKYO PRO Market等で確認済みキャッシュがある場合はJPX新規上場資料または会社IRの内容を使用
5. 日本語概要がまだ空の場合だけEDINET DBプロフィール
6. 最後まで日本語化できない場合は英語原文を暫定表示、英語も無ければデータなし

EDINET DBよりGPTを先にする理由は、Freeプラン100回/日を財務・株主・役員や、本当に概要が無い銘柄へ温存するため。正確性の観点では出典を必ず残し、GPT生成文は「Yahoo英語概要 + OpenAI日本語要約」と記録する。

四季報オンラインの特色・記事は記者による著作物であり、GPTで言い換えても安全な取得元にはならない。`stock_analyzer.py` に残っている四季報HTMLフォールバックは撤去対象。

### 財務

1. yfinanceを最新値の第一取得先として継続
2. EDINET XBRLで年次BS・PL・CFを公式値として補完・検算
3. J-Quantsは遅延を許容できる検算・補助候補
4. 取得失敗時は以前の正常値を保持し、`stale` と基準日を表示

EDINETは会計基準や企業固有タグの差があるため、売上高・営業利益・経常利益・純利益・総資産・純資産・営業CF等から小さく実装し、未対応タグをログ化して増やす。

### 株主・役員

1. EDINET有価証券報告書の「大株主の状況」「役員の状況」を第一の公式フォールバックにする
2. 新規上場時はJPX新規上場資料
3. 更新が必要なら株主総会招集通知・会社IR
4. Strainer/J-LiCは補助扱い
5. `該当なし` と `取得失敗` をUIで分ける

株主・役員は日次更新不要。年1回または新しい有価証券報告書・招集通知が出たときだけ更新すればよい。

### 設立日・上場日

- 上場日: JPXの上場銘柄情報・新規上場資料を正本とし、yfinance初回取引日は欠損時だけ利用。
- 設立日: EDINETの会社情報、JPX新規上場資料、会社公式プロフィールから取得。
- 一度公式確認した値は頻繁に変わらないため、永続キャッシュしてよい。

### 業績予想

1. Yahoo日本版の業績ページを現在値の第一取得先として残す
2. Yahooが全欠損・部分欠損の場合だけEDINET DBの`earnings`で不足値を補完する
3. 取得日と対象決算期を保存し、古い予想を現行値として扱わない
4. TDnetの決算短信・業績予想修正資料は公式候補だが、正式APIは有料のため無料運用には組み込まない

株探は公式ヘルプでプログラムによる機械取得・スクレイピングを禁止しているため、業績予想の取得元・フォールバックには使用しない。画面上の数値が確認できた場合も、同じ会社発表値をYahoo日本版、TDnet、JPX掲載の決算短信または会社IRから取得する。

- 株探「掲載情報をシステムで自動的に取得することは禁止」: https://support.kabutan.jp/hc/ja/articles/42828867759129
- 個別銘柄だけ再取得する場合: `python backfill_yahoo_fields.py --code 7089`
- 7089は2026-08-05の確認時点で、Yahoo `/performance`から2027年3月期の会社予想（売上64.0億円、営業利益14.0億円、経常利益13.0億円、純利益9.4億円）を既存パーサーで取得できた。欠損原因はパーサーではなくDB行が再取得前だったためで、個別バックフィルで復旧済み。正本は2026-05-08公表のJPX掲載決算短信。

無料のTDnet閲覧サービスは直近31日分を確認できるが、汎用の無料APIではない。2026年5月開始のJ-Quants TDnet書類アドオンもLightプラン以上に月額11,000円が必要。会社IR・無料閲覧ページのPDF抽出は会社ごとの形式差と再配信条件があるため、第2段階とする。

### 信用倍率

信用倍率は会社の本質的な財務評価ではなく、市況・需給データ。Yahoo日本版を第一取得先とし、空の場合はJPX公式の「銘柄別信用取引週末残高」PDFから売残・買残を取得して倍率を計算する。JPX値は毎週第2営業日公表の週次データなので、画面に`JPX週次`と基準日を表示する。JPXにも未掲載なら、値を推測せず`取得できたときだけ表示`を維持する。

## EDINET DB API 実装記録（2026-08-05）

ユーザーが発行したキーは金融庁の公式EDINET APIキーではなく、Cabocia運営の第三者サービス「EDINET DB」のAPIキー。ベースURLは `https://edinetdb.jp/v1`、認証は `X-API-Key`。

実装:

- `edinet_db_client.py`: 証券コード→EDINETコード検索と欠損補完
- `stock_analyzer.py`: 通常の単一銘柄分析時だけ、Yahoo等の取得後に補完を実行
- `summary_translation.py`: Yahoo英語概要をGPTで日本語要約。概要についてはEDINET DBより先に実行
- `render.yaml`: APIキー・日次上限・安全余力・キャッシュ時間を環境変数化
- `templates/stock_detail.html` / `_report_body.html`: EDINET DBを実際に使った場合だけ出典と免責を表示
- 四季報オンラインHTMLのフォールバックは利用条件と著作物リスクを避けるため撤去

環境変数:

```env
EDINETDB_API_KEY=（マイページで発行したキー）
EDINETDB_DAILY_LIMIT=100
EDINETDB_DAILY_RESERVE=10
EDINETDB_CACHE_HOURS=24
EDINETDB_TIMEOUT=20
```

動作方針:

- 既に取得済みの値はEDINET DBで上書きしない。
- 事業概要・会社属性、財務、主要株主、役員、業績予想のうち欠けている種類だけ呼ぶ。
- 事業概要は `Yahoo日本語 → Yahoo英語+GPT → 確認済み公式キャッシュ → EDINET DB`。画面の「日本語を再取得」も同じ順序。
- Yahoo Japan、J-LiC、Strainerは個別に失敗処理し、1つが例外になっても残りの無料ソースを試してからEDINET DBへ進む。
- 1銘柄の最大は検索を含め6リクエスト。90回使用時点（初期値）で自動停止し、残り10回を安全余力として残す。
- APIレスポンスの `X-RateLimit-Remaining` も監視し、残数が安全余力以下なら追加取得しない。
- 429、認証失敗、未収録、タイムアウト、日次枠温存を `source_status.edinet_db` に保存する。
- 高速バッチ `skip_extras=True` では無料枠を大量消費しないためEDINET DBを呼ばない。
- 株主・役員は最新年度だけを使い、財務は直近5年を使う。
- 財務比率は単位の取り違えを避けるため、可能な限り売上・利益・総資産・純資産・EPS・DPSからアプリ側で再計算する。

注意:

- EDINET DBのFreeプランは100リクエスト/日。`/usage`も1回に数えられるため、通常処理では呼ばない。
- 公開サービスでは「Powered by EDINET DB」等の出典表示と免責が必要。
- API取得データの一括再配布やEDINET DB相当のラッパーAPIは禁止。
- 164A（アップルパーク）は2026-08-05時点のEDINET DB検索で未収録。TOKYO PRO Market銘柄のため、既存のJPX新規上場資料・会社公式開示キャッシュが正本。
- APIキーはGitに入れない。ローカル `.env` とRenderのSecretにだけ設定する。

### 業績予想・信用倍率の改善記録（2026-08-05）

- 業績予想はYahoo Japan `/performance`を先に試し、全欠損だけでなく部分欠損でもEDINET DB `earnings`から不足項目だけ補完する。
- Yahooの`forecast`に決算期だけがあり数値が無い場合は、取得失敗ではなく`not_disclosed`（会社予想非開示）として記録する。予想年だけをDBへ保存して「取得済み」に見せない。
- 数値文字列、カンマ、0、赤字予想の負数も抽出対象。会社予想非開示はEDINET DBへ切り替えても値が存在しないため、スコアでは「会社予想非開示」と表示して計算から除外する。
- YahooとEDINET DBの既存値は互いに上書きせず、取得できた項目を統合する。
- 業績予想の取得元・状態は`source_status.forecast`へ保存する。
- 全銘柄の穴埋めは`backfill_yahoo_fields.py --edinet-forecasts --limit 20`で実行できる。Yahooが空の銘柄だけEDINET DBの`earnings`に限定して呼び、プロフィール・財務・株主・役員APIは消費しない。会社予想非開示ではEDINET DBを呼ばない。
- 3089（テクノアルファ）は実確認でYahoo `/performance`自体はHTTP 200だが、2026年11月期の`forecast`には決算期・更新日だけで数値が無かった。これはブロックではなく会社予想非開示として扱う。設立日はYahooプロフィールの1989年12月22日、上場日は会社公式IRの2007年10月10日を出典付きでDBへ保存済み。
- 信用倍率はYahoo Japanの取得が空の場合、`jpx_margin.py`でJPX公式の最新週次PDFを取得する。
- JPX PDFは12時間プロセス内キャッシュし、取得失敗は5分後に再試行する。銘柄別の売残・買残から倍率を計算する。
- JPX週次値は`source_status.margin_trading`へ出典・基準日・取得日時を保存し、画面にも`JPX週次`と基準日を表示する。
- TOKYO PRO Market等でJPX週次信用残高に未掲載の場合は`no_data`とし、値を推測しない。

### 画面表示の補足（2026-08-05）

- 共通上部ヘッダーはスクロール中も上端に固定する。
- `/screener`の銘柄詳細と、銘柄詳細の「レポートを見る」は新しいタブで開く。
- 銘柄詳細の会社名直下では、上段に銘柄コード・設立日、下段に業種・上場日を2列の会社基本情報として表示し、値の途中で折り返さない。
- 指標グリッドでは、配当利回りの直下にゴールデンクロス、時価総額の直下にデッドクロスを同じ大きさのカードで表示する。
- 配当利回りが欠損でも取得済みDPSが0円なら、`---`ではなく`0% / 無配`と表示する。DPSも不明なら無配と推測せず`---`を維持する。

### Phase 4: 運用監視

- 取得元ごとの成功率とHTTP状態を日次集計
- 同一取得元の429・5xx急増を通知
- 取得元のHTML変更を「全銘柄no_data」と誤認しない
- 銘柄画面に出典・基準日・最終取得日を表示

## 再調査が必要になる条件

次の場合だけ、この文書の前提を再確認する。

- EDINET、JPX、J-Quants、Yahooの仕様・規約が変わった
- 取得成功率が急落した
- `source_status` と画面表示が矛盾した
- 新しい取得元を本番・公開サービスへ組み込む
- OpenAIのモデルまたはSDKを変更する
